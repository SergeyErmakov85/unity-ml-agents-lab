# 07_TROUBLESHOOTING — Ошибки и решения

Документ накапливается по ходу работы. Сюда попадают **только фактически
встреченные** проблемы с их фактическим решением, а не гипотезы.

Формат записи: симптом → причина → решение → откуда известно.

## Установка окружения

### T-1. `mlagents-envs` не ставится под Python 3.11+

**Симптом.** `pip install mlagents-envs` сообщает, что ни одна версия не подходит.

**Причина.** `setup.py` пакета содержит `python_requires=">=3.10.1,<=3.10.12"`.
Источник: `ml-agents-envs/setup.py` тега `release_23_tag`.

**Решение.** Установить Python 3.10.11 и создать окружение именно на нём:

```powershell
winget install --id Python.Python.3.10 --version 3.10.11 --scope user --silent
py -3.10 -m venv python\.venv
```

**Дата:** 2026-08-15.

### T-2. Клонирование `ml-agents` с GitHub идёт со скоростью ~16 КБ/с

**Симптом.** `pip install "git+https://github.com/Unity-Technologies/ml-agents.git@release_23_tag#subdirectory=ml-agents-envs"`
висит на стадии `Cloning …` десятки минут; каталог клона растёт примерно
на 1 МБ в минуту. `git clone --depth 1` ведёт себя так же.

**Причина.** Ограничение скорости именно на git/codeload-эндпоинтах GitHub.
Проверено: `raw.githubusercontent.com` и `packages.unity.com` в тот же момент
отдают данные на нормальной скорости (32 МБ пакета Unity скачались за секунды).

**Решение.** Скачать файлы подкаталога `ml-agents-envs` пофайлово через
`raw.githubusercontent.com` (список файлов — через `api.github.com`
`git/trees/release_23_tag:ml-agents-envs?recursive=1`) и поставить из локального
каталога. Код при этом ровно тот же — тег определяет содержимое файлов.

Проверка, что установлен нужный код:

```powershell
.\python\.venv\Scripts\python.exe -c "import mlagents_envs; print(mlagents_envs.__version__, mlagents_envs.__release_tag__)"
```

`__release_tag__` обязан быть `release_23_tag`.

**Дата:** 2026-08-15.

### T-3. Конфликт версий `numpy` и `protobuf` в стеке

**Симптом.** Свежие `onnx`, `onnxruntime`, `tensorboard` тянут `protobuf>=4`
и `numpy>=2`, а `mlagents-envs` требует `numpy>=1.23.5,<1.24.0` и
`protobuf>=3.6,<3.21`.

**Причина.** `mlagents-envs@release_23_tag` заморожен на старых границах;
источник — его `setup.py`.

**Решение.** Границы всего стека подчинены ML-Agents; они зафиксированы
в `python/pyproject.toml` с объяснением. Проверка — `pip check`, вывод
приложен к `docs/01_STACK.md` (требование 4.4).

**Дата:** 2026-08-15.

## Обучение и связка Python ↔ Unity

### T-7. Повторный `env.reset()` стоит одного шага с нулевым действием

**Симптом.** Оценка политики в `E01_GridWorld` давала среднюю награду
**0.688** при точно посчитанном оптимуме **0.68** — результат «лучше
оптимального». Разбор длин эпизодов показал: первый эпизод после сброса
занимает 7 шагов, все последующие — 8.

**Причина.** Наблюдение, возвращаемое сразу после **повторного**
`UnityEnvironment.reset()`, соответствует состоянию **после** одного шага
с нулевым действием, а не начальному состоянию эпизода. Первый сброс
(в момент подключения) этим не страдает.

Измерение на реальном билде (агент стартует в клетке (0,0) = состояние 0,
действие 0 = «север»):

```
A: только reset внутри open_unity_env  -> состояния [0, 0, 0, 0]
B: open_unity_env + ещё один reset()   -> состояния [5, 5, 5, 5]   # (0,1)
C: open_unity_env + два reset()        -> состояния [5, 5, 5, 5]   # не накапливается
```

Эффект не накапливается: каждый сброс перезапускает эпизод и применяет ровно
один нулевой шаг.

**Чем это опасно.** Ошибка не роняет обучение и не даёт исключений. Она
завышает приёмочные числа (эпизод короче — награда выше) и портит первый
переход каждого эпизода после сброса: агент уже сдвинулся, а обучающая
выборка считает, что он в старте.

**Решение — два независимых изменения.**

1. `VecUnityEnv.reset()` **не сбрасывает уже сброшенную среду**: обёртка
   отслеживает флаг `UnityEnvHandle.stepped_since_reset`. Пропуск безопасен —
   сбрасывать нечего, а вызов стоил бы шага.
2. Оценка политики (`labrl.train.tabular.evaluate_greedy`) **не сбрасывает
   среду вовсе**. Вместо сброса — «прогрев»: эпизоды, начатые под ε-жадной
   политикой, доигрываются жадной и отбрасываются, а замеряются только
   эпизоды, целиком прожитые жадной политикой.

Покрыто тестами `test_reset_is_skipped_when_nothing_was_stepped` и
`test_reset_is_performed_after_a_step`.

**Дата:** 2026-08-15.

### T-10. Сокращённый прогон проваливается, если сжать вместе с ним расписание ε

**Симптом.** `E03_RollerBall`, DQN, 6000 шагов. Через CLI — награда **0.9394**,
успех 100 %. Тот же бюджет из ноутбука — **−0.1169**, успех 50 %.

**Разбор.** Сначала была проверена гипотеза «разброс»: три быстрых прогона CLI
на сидах 0, 1, 2 дали 0.9394 / 0.9522 / 0.9515 — разброса нет, причина
систематическая.

Отличий у ноутбука было два: расписание ε сжато пропорционально бюджету
(`decay_steps = TOTAL_STEPS * 0.5` = 3000 вместо 30000) и оценка каждые
2000 шагов вместо одной в конце. Обе гипотезы проверены по отдельности:

| Конфигурация | Результат на 6000 шагов |
|---|---|
| `decay_steps=30000`, оценка в конце (CLI по умолчанию) | **+0.9394** |
| `decay_steps=30000`, оценка каждые 2000 | **+0.9460** |
| `decay_steps=3000`, оценка каждые 2000 (как было в ноутбуке) | **−0.1169** |

Причина — **сжатие расписания разведки**, а не частота оценок.

**Почему так.** При 6000 шагов и `learning_starts=2000` выполняется около 4000
обновлений. К шагу 3000 жадная политика ещё плоха, а ε уже упало до 0.05:
буфер начинает наполняться узкими траекториями плохой политики. Высокое ε,
наоборот, продолжает поставлять разнообразные переходы, и тех же 4000
обновлений хватает.

**Решение.** Сокращённый прогон должен быть **началом полного**, а не другим
экспериментом: при уменьшении бюджета расписания, заданные в абсолютных шагах,
не масштабируются. В ноутбуке `decay_steps` зафиксировано на 30000 независимо
от `QUICK_RUN`; `scripts/train.py` изначально берёт `decay_steps` из конфига
и потому этой ошибке не подвержен.

**Общий вывод.** Режим быстрой проверки (требование 9.3) обязан отличаться от
полного **только длительностью**. Любой другой изменённый параметр превращает
смоук-тест в измерение чего-то другого.

**Дата:** 2026-08-15.

### T-9. Экспорт в ONNX падает, если сеть обучалась на GPU

**Симптом.** Обучение проходит полностью, а на экспорте:

```
RuntimeError: Expected all tensors to be on the same device,
but found at least two devices, cuda:0 and cpu!
```

**Причина.** `torch.onnx.export` трассирует модуль фиктивными входами. Модуль
после обучения находится на CUDA, а фиктивные входы создавались на CPU.

**Решение.** Экспорт **всегда** выполняется на CPU: модуль временно переносится
и возвращается на исходное устройство (`labrl.export.onnx_export`,
`_module_device`). То же сделано в верификации: сравнение с PyTorch идёт на CPU,
там же, где onnxruntime исполняет граф.

Это не обход ошибки, а правильное поведение по существу: результат экспорта
не должен зависеть от того, была ли на машине видеокарта.

**Дата:** 2026-08-15.

### T-8. Модель, назначенная из редакторного скрипта, не попадает в билд

**Симптом.** Инференс-билд `E01_GridWorld` собирался успешно, запускался без
единой ошибки в логе, но агент не двигался: эпизоды заканчивались только
по `MaxStep`, `Goal` не достигался ни разу, средняя награда 0.

Диагностика показала: `Academy` проинициализирована, `StepCount` растёт,
`CompletedEpisodes` растёт, `OnEpisodeBegin` вызывается — а `OnActionReceived`
**не вызывается ни разу**.

**Причина.** Редакторный скрипт присваивал `behavior.Model` и
`behavior.BehaviorType` обычным присваиванием свойств. Агенты живут внутри
инстансов префаба `TrainingArea`, и правка поля инстанса **из кода** не создаёт
prefab-override автоматически: `EditorSceneManager.SaveScene` сохранил сцену
с исходными значениями. В билде поведение осталось `Default` без модели, а
`Default` без модели и без коммуникатора даёт `HeuristicPolicy`. Агент
«управлялся клавиатурой», которой в headless-билде нет, — отсюда неподвижность.

Ошибка не даёт ни исключения, ни предупреждения: билд собирается, игрок
запускается, просто ничего не происходит.

**Решение.** После присваивания:

```csharp
behavior.Model = model;
behavior.BehaviorType = BehaviorType.InferenceOnly;
PrefabUtility.RecordPrefabInstancePropertyModifications(behavior);
EditorUtility.SetDirty(behavior);
```

плюс `EditorSceneManager.MarkSceneDirty(scene)` перед сохранением.

Дополнительно `InferenceBuild` **перечитывает сохранённую сцену** и проверяет,
что модель и тип поведения записаны (`VerifySaved`). Проверка стоит секунды
и ловит регресс до шестиминутной сборки.

**Как отличить этот случай от «модель плохая».** Признак именно этой поломки —
`OnActionReceived` не вызывается вообще. Если модель загружена, но плохая,
метод вызывается, а действия просто неудачны.

**Дата:** 2026-08-15.

### T-11. Табличный метод с постоянным α даёт колеблющуюся политику

**Симптом.** `E02_CartPoleUnity`, табличный Q-learning с фиксированным
α = 0.15, бюджет 150 000 шагов. Оценка жадной политики не сходится,
а скачет от точки к точке:

```
шаг   60000: 131.15      шаг  100000: 100.30
шаг   70000: 190.50      шаг  110000: ...
шаг   80000:  35.45      шаг  130000: 107.10
шаг   90000: 197.60      шаг  150000: ...
```

Итог прогона при этом становится лотереей: приёмочное число берётся
из последней оценки, а она с равной вероятностью может оказаться и 197,
и 35.

**Причина.** Условие сходимости Роббинса–Монро требует убывающего шага
обучения: Σα = ∞ и Σα² < ∞. При **постоянном** α таблица не сходится,
а бесконечно колеблется вокруг решения с амплитудой порядка α·|TD-ошибка|.

На задачах предсказания это почти незаметно — оценка «дрожит» вокруг верной.
На задачах **управления** это фатально: политика — это `argmax` по строке
таблицы, и колебание двух близких значений переворачивает выбор действия
целиком. Одна перевёрнутая ячейка в часто посещаемой области роняет эпизод.

Усугубляет дело дискретизация: внутри ячейки лежат разные ситуации, поэтому
TD-ошибка не стремится к нулю даже у сошедшегося метода, и колебание
не затухает само.

**Решение.** Расписание α, как у ε. В `configs/E02_CartPoleUnity__qlearning.yaml`:

```yaml
algo:
  learning_rate:
    type: linear
    start: 0.20
    end: 0.01
    decay_steps: 120000     # 80% бюджета на спад шага обучения
```

Поддержка: `QLearning.set_learning_rate()`, параметр `lr_schedule`
у `labrl.train.tabular.train_q_learning`, разбор блока — в
`scripts/train.py::learning_rate_schedule`. Блок `learning_rate` конфига
принимает и число (постоянное α — сознательный выбор пользователя),
и расписание.

**Результат после исправления** (тот же сид, тот же бюджет):

```
шаг  110000: 200.00      шаг  130000: 195.75
шаг  120000: 200.00      шаг  150000: 199.05
```

**Обобщение.** То же относится к любому табличному методу на задаче
управления. У методов с нейросетью проблема выражена слабее: Adam сам
масштабирует шаг, а сглаживание сети связывает соседние состояния — но
и там DQN колеблется (см. `docs/envs/E03_RollerBall.md`, «Наблюдение
об устойчивости»).

**Дата:** 2026-08-15.

### T-12. Непрерывное действие обязано проходить то же приведение диапазона, что и в графе ONNX

**Симптом (потенциальный, предотвращён проверкой).** Агент с непрерывными
действиями обучается в Python до высокой награды, а в Unity ведёт себя
заметно слабее — при том, что верификация ONNX проходит все 13 проверок.

**Причина.** Обёртка экспорта приводит выход политики к диапазону Unity
преобразованием `clamp(x, −3, 3) / 3` (контракт §4.2). Если при сборе опыта
в Python действие уходило в среду **сырым**, то обучение шло в одной системе
координат, а инференс в Unity идёт в другой: одно и то же число означает
разную величину воздействия. Верификация ONNX этого не ловит — она сравнивает
граф с PyTorch-модулем, а не с тем, что делал цикл обучения.

**Решение.** Приведение вынесено в одну функцию
`labrl.nets.gaussian_policy.to_env_action`, и она вызывается в обоих местах:
в `A2C.act` / `PPO.act` (сбор опыта) и в `deterministic_action` (оценка).
Тест `python/tests/test_onpolicy.py::test_deterministic_action_matches_onnx_graph`
прогоняет настоящий граф через `onnxruntime` и сравнивает с
`algo.deterministic_action`; расхождение больше 1e-6 роняет тест.

Та же проверка продублирована в ячейке 9 ноутбуков `E04_BallBalance__*`:
она выполняется на **реальных** наблюдениях среды непосредственно перед
копированием модели в проект Unity.

**Дата:** 2026-08-15.

### T-13. On-policy метод разрушает уже выученную политику после того, как задача решена

**Симптом.** `E04_BallBalance`, PPO, бюджет 100 000 шагов. Награда доходит
до максимума и обваливается:

```
шаг  20000:  91.08      шаг  60000:  32.34
шаг  40000: 100.00      (далее эпизоды по 1.9 и 8.3)
```

Ни `Approx KL` (0.002–0.011), ни `Clip Fraction` (0.03–0.06) при этом
не показывают ничего необычного — по всем признакам шаг PPO аккуратный.

**Причина.** Когда задача решена, среда перестаёт различать поведения:
каждый шаг даёт +0.1, эпизоды не заканчиваются, и суммарная награда
эпизода — константа 100. Значит:

* критик сходится к константе, `Losses/Value Loss` → 0.000;
* все TD-ошибки δ_t обращаются в ноль, и в оценке преимущества остаётся
  **только ошибка критика** — шум;
* `normalize_advantage` делит преимущества на их стандартное отклонение,
  то есть возводит этот шум обратно в **единичный** масштаб.

В результате политика получает полноразмерный градиент, не связанный
с качеством действий, и начинает случайно блуждать. Диагностический признак —
`Custom/Explained Variance` уходит в минус (−0.64, −0.69) при `Value Loss`
около нуля: критик «не объясняет» цель просто потому, что объяснять нечего.

Обрезка PPO здесь не помогает: она ограничивает **размер** шага, а не его
осмысленность, и блуждание идёт мелкими законными шагами.

**Решение.** Затухающий шаг обучения — то же, что делает штатный тренер
ML-Agents (`learning_rate_schedule: linear` — его значение по умолчанию):

```yaml
algo:
  learning_rate:
    type: linear
    start: 0.0003
    end: 0.0
    decay_steps: 100000
```

Поддержка: `A2C.set_learning_rate()` / `PPO.set_learning_rate()`, параметр
`lr_schedule` у `labrl.train.onpolicy.train_on_policy`. По мере затухания
блуждание становится всё мельче, и политика остаётся там, где сошлась.

Дополнительно снижен `entropy_coef` с 0.005 до 0.001 (значение штатного
конфига 3DBall): бонус за энтропию — второй источник шума в уже сошедшейся
политике.

**То же самое у A2C, только сильнее.** У A2C нет обрезки, а батч на порядок
меньше (128 переходов против 1024 у PPO), поэтому нормировка шумит ещё
заметнее. Здесь помогло не затухание шага, а **отключение самой нормировки** —
как и сделано в эталонных реализациях A2C:

```yaml
algo:
  normalize_advantage: false
```

Без нормировки величина шага пропорциональна истинному преимуществу и сама
сходит на нет, когда учиться уже нечему. Измерено на `E04_BallBalance`
(один и тот же сид, один и тот же бюджет 100 000 шагов):

| Настройка | 20 000 | 40 000 | 60 000 | 100 000 |
|---|---|---|---|---|
| `normalize_advantage: true` | 9.7 | 65.0 | 33.3 | **45.3** |
| `normalize_advantage: false` | 15.7 | 95.7 | 95.8 | см. карточку среды |

Значение по умолчанию `A2CConfig.normalize_advantage` изменено на `false`;
у `PPOConfig` оно осталось `true` — там батч больше, а обрезка ограничивает
шаг.

**Третий рычаг — размер батча.** У PPO разброс между сидами (100.0 против
78.2 при пороге 80) снялся увеличением роллаута со 128 до 512 шагов, то есть
батча с 1024 до 4096 переходов: чем больше выборка, тем меньше нормировка
раздувает случайные отклонения. Штатный тренер ML-Agents на этой же задаче
копит 12 000 переходов на обновление.

**Чего делать не следует.** Брать в качестве приёмочного числа лучшую оценку
за прогон вместо последней. Это скрыло бы проблему, а не устранило: агент,
которого нужно «поймать в удачный момент», не воспроизводим.

**Дата:** 2026-08-15.

### T-14. Быстрый прогон ноутбука затирает модель полного обучения

**Симптом.** Проверка инференса `E02_CartPoleUnity` дала 200.00 из 200 —
все 20 эпизодов прожиты до конца. Через час та же команда на той же среде
дала **175.45**: десять эпизодов из двадцати закончились падением шеста.
Ни модель, ни код между запусками не менялись — менялся файл модели.

**Причина.** Ноутбук и `scripts/train.py` пишут обученную модель по одному
и тому же пути `Assets/Envs/E##_<Name>/Models/*.onnx`. Запуск ноутбука
в режиме `QUICK_RUN = True` — а он предусмотрен требованием 9.3 и выполняется
при каждой проверке «Restart & Run All» — кладёт туда модель смоук-теста.
Файл остаётся валидным и проходит все 13 проверок контракта, поэтому ничто
не сигнализирует об ошибке: в Unity просто уезжает агент, обученный
за 15 000 шагов вместо 150 000.

**Решение.** `scripts/sync_models.py` возвращает в проект Unity модель
**последнего полного** прогона каждой пары (среда, алгоритм):

```powershell
python scripts\sync_models.py            # показать расхождения
python scripts\sync_models.py --apply    # скопировать
```

Быстрые прогоны отбрасываются по признаку `quick` из `env_info.json` — тому же,
по которому их отбрасывает `scripts/results.py`.

**Подводный камень внутри решения.** Ноутбуки Фазы 2 записывали `env_info.json`
**без** поля `quick`, поэтому первая версия `sync_models.py` считала быстрый
прогон ноутбука полным и оставляла его модель на месте. Именно из-за этого
и было получено значение 175.45. Все ноутбуки теперь пишут
`{"total_steps": TOTAL_STEPS, "quick": QUICK_RUN}`.

**Правило.** Перед проверкой по требованию 10.6 и перед коммитом — выполнять
`sync_models.py --apply`. Порядок в конвейере: обучение → ноутбуки → синхронизация
моделей → проверка инференса.

**Масштаб проблемы оказался шире, чем один пример.** При первом же применении
скрипта выяснилось, что в репозитории с Фазы 2 лежала модель `E03_RollerBall`
из быстрого прогона ноутбука, а не из полного обучения: ноутбук выполнялся
последним и затёр файл уже после того, как приёмочная проверка прошла. Обе
модели проходят контракт ONNX и обе работают в Unity — расхождение видно
только по награде.

**Дата:** 2026-08-15.

### T-6. Unity в batch-режиме зависает на инициализации Asset Database

**Симптом.** `Unity.exe -batchmode -quit -executeMethod …` доходит до строки
`Application.AssetDatabase Initial Refresh Start` и замирает: лог не растёт,
процесс жив и «отвечает», но потребляет 4–5 секунд CPU за десять минут.
Повторный запуск падает сразу после `Successfully changed project path`
с кодом возврата 1 — потому что предыдущий, зависший процесс всё ещё держит
`Temp/UnityLockfile`.

**Причина.** Пакет `com.unity.ai.assistant` 2.15.0-pre.1 (облачный редакторный
помощник в статусе pre-release). Первый импорт проекта после его удаления из
`manifest.json` прошёл до конца за ~3 минуты: 3,2 МБ лога, 98 с CPU,
`ProjectBootstrap` отработал, код возврата 0.

**Решение.**

1. Снять зависшие процессы и удалить lock-файл:

   ```powershell
   Get-Process -Name "Unity","UnityPackageManager","UnityCrashHandler64" -EA SilentlyContinue | Stop-Process -Force
   Remove-Item .\unity\MLAgentsLab\Temp\UnityLockfile -Force -EA SilentlyContinue
   ```

2. Убрать `com.unity.ai.assistant` из `Packages/manifest.json` (допущение A-22).

**Диагностический приём.** `& $unity …` в PowerShell не всегда заполняет
`$LASTEXITCODE` для отсоединившегося процесса Unity — код возврата надёжно
виден через `Start-Process -PassThru -Wait` и `$proc.ExitCode`.

**Дата:** 2026-08-15.

### T-5. `TensorNames` из ML-Agents недоступен из кода проекта

**Симптом.** `Unity.MLAgents.Inference.TensorNames` не виден из скриптов
в `Assets/`.

**Причина.** Класс объявлен `internal` (проверено в
`com.unity.ml-agents@4.0.3/Runtime/Inference/TensorNames.cs`). То же относится
к `SentisModelInfo`, поэтому и `SentisModelParamLoader.CheckModel` фактически
недоступен снаружи сборки пакета.

**Решение.** `Assets/Shared/Editor/OnnxContractCheck.cs` дублирует имена
тензоров строковыми константами, сверенными с исходником пакета, и работает
через публичный `Unity.InferenceEngine.ModelLoader` / `Model.inputs` / `Model.outputs`.

**Дата:** 2026-08-15.
