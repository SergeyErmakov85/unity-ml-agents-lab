# ppo_discrete — PPO с категориальной политикой

**Урок:** 2.2 «PPO с нуля» (метод) и 3.3 «Учебный план» (применение),
`https://rl-cuber-unity-code.com/courses/2-2`
**Реализация:** `python/labrl/algos/ppo_discrete.py`
**Класс:** `PPODiscrete` / конфиг: `PPOConfig` (тот же, что у непрерывного PPO)
**Семейство:** policy gradient, actor-critic, on-policy
**Применим к:** действия дискретные (одна или несколько веток), наблюдения векторные

## Это не другой алгоритм

Правило обновления, обрезка отношения правдоподобий, GAE и функция потерь —
те же, что в [`ppo`](ppo.md). Метод `update()` **наследуется без изменений**:
две реализации одной математики рано или поздно разойдутся, и тогда сравнение
дискретного и непрерывного случая будет сравнивать не задачи, а расхождение
(требование 8.7).

Отличие ровно в двух местах, и оба живут в **распределении политики**,
а не в алгоритме:

| что | непрерывный случай | дискретный случай |
|---|---|---|
| распределение | гауссиана `N(μ(s), σ)` | произведение категориальных по веткам |
| что возвращает сеть | среднее `μ(s)` | логиты всех веток подряд |
| сэмплирование | `μ + σ·ε`, `ε ~ N(0,1)` | `multinomial(softmax)` по каждой ветке |
| энтропия | зависит только от `σ` | зависит от наблюдения |
| действие для среды | float в `[−1, 1]` | целые индексы `(B, ветки)` |

Последняя строка объясняет, почему у дискретного случая нет разделения
на «сырое» и «приведённое» действие: индекс ветки уже и есть то, что уходит
в среду.

Предпоследняя строка — единственное, что потребовало правки в `PPO`:
конструктор определяет **по сигнатуре** `policy_net.entropy`, нужно ли ей
наблюдение. Гауссова политика отвечает «нет», категориальная — «да».
Это одна строка вместо копии всего метода.

## Факторизация по веткам

Действие может состоять из нескольких независимых решений (у `E08_SoccerArena`
их три: ход, движение боком, поворот). Тогда

```
π(a | s) = π₀(a₀ | s) · π₁(a₁ | s) · π₂(a₂ | s)
```

и логарифмы складываются, а энтропии суммируются. Альтернатива — одно
распределение на все `3 × 3 × 3 = 27` комбинаций — потребовала бы 27 логитов
вместо 9 и учила бы каждую комбинацию отдельно: «вперёд + вправо» не помогало
бы выучить «вперёд + влево».

**Практическое следствие для `entropy_coef`.** Стартовая энтропия равна
`Σ ln(размер ветки)`: для трёх веток по три действия это `3·ln3 ≈ 3.3` нат,
для одной ветки из четырёх — `ln4 ≈ 1.4`. Коэффициент, взятый из одноветочной
среды, даст втрое более сильный бонус, и политика останется случайной.

## Требования к сети

Любой `nn.Module`, возвращающий `(B, sum(branches))` логитов и реализующий:

| метод | что возвращает |
|---|---|
| `log_prob(obs, action)` | `(B,)` — сумма по веткам |
| `entropy(obs)` | скаляр — сумма энтропий веток, усреднённая по батчу |
| `sample(obs)` | `((B, ветки) индексов, (B,) log π)` |
| `greedy(obs)` | `(B, ветки)` — argmax каждой ветки |

Готовая реализация: `labrl.nets.categorical_policy.MultiBranchCategoricalPolicy`.

## Экспорт в ONNX

Стратегия `categorical` (`labrl.export.onnx_export`): `discrete_actions`
получается сэмплированием из softmax, `deterministic_discrete_actions` —
argmax. Оба выхода **целые**: Unity читает их как `Tensor<int>`
(`Runtime/Inference/ApplierImpl.cs`), и приведение к float ломает инференс,
оставляя ONNX формально валидным.

`PPODiscrete.deterministic_action` обязан совпадать с
`deterministic_discrete_actions` графа — иначе оценка в Python и инференс
в Unity выбирают разное, и проверка 10.6 провалится по причине, не имеющей
отношения к обучению.
